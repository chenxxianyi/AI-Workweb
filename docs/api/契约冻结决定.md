## 3.1 限流（C-14，F08 补充）

| 接口 | 窗口内上限 | 实现 |
|---|---|---|
| `POST /auth/recovery/complete` | 5 次 / 60 秒（按 IP + 方法 + 路径） | `@RateLimit({ limit: 5, ttlMs: 60_000 })` |
| `PATCH /auth/password` | 10 次 / 60 秒 | `@RateLimit({ limit: 10, ttlMs: 60_000 })` |
| `POST /auth/login`（F09） | 默认 10 次 / 60 秒，另按账号计数 | F09 实现 |
| 其他接口 | 不设默认全局限流 | 需要时按接口显式加 |

超限返回 `429 RATE_LIMITED`，`error.details.retryAfterSeconds` 给出建议等待秒数。
计数在进程内，多实例部署不共享（本期单机部署可接受，F43 按部署形态复核）。

## 3.2 会话与 CSRF 落地细节（C-15，F09 补充）

| 项 | 决定 |
|---|---|
| Cookie 名 | 会话 `sfs_session`（`HttpOnly`、`SameSite=Lax`、`Path=/`，HTTPS 加 `Secure`）；CSRF `sfs_csrf`（**非** HttpOnly，供前端读取） |
| 会话令牌 | 32 字节随机 base64url；数据库只存 SHA-256；空闲 24h、绝对 7 天；每 60 秒最多续期一次 |
| 登录轮换 | 每次登录新建会话（多设备并存），并轮换 CSRF 令牌；旧 CSRF Cookie 被覆盖 |
| CSRF 校验 | 已登录：`X-CSRF-Token` 的 SHA-256 等于会话 `csrf_token_hash`；未登录（登录）：双提交（头 == `sfs_csrf` Cookie） |
| 来源校验 | 只要请求带 `Origin`／`Referer`，就必须与 `PUBLIC_ORIGIN` 同源；两者都没有时放行（curl/测试），仍受 CSRF 令牌约束 |
| 豁免 | `@CsrfExempt()`：`POST /auth/recovery/complete`（持有型一次性令牌，非 Cookie 凭据） |
| 默认鉴权 | 全局 `SessionAuthGuard`：除 `@Public()`（health、`GET /auth/csrf`、`POST /auth/login`、`POST /auth/recovery/complete`、`GET /auth/csrf-cookie-name`）外都需登录 |
| 登录锁定 | 15 分钟内失败 5 次 → `429 RATE_LIMITED`（`details.retryAfterSeconds`），成功登录清零；按账号计数，进程内 |
| 会话管理 | `GET /auth/sessions`（自己全部有效会话，标记 current）、`DELETE /auth/sessions/{id}`（非本人 404）、`DELETE /auth/sessions`（吊销其他设备） |
| 重启 | 会话存数据库，进程重启不影响已登录设备；`SessionAuthGuard` 每次请求查库 |

## 3.3 空间与成员（C-16，F10 补充）

| 项 | 决定 |
|---|---|
| 角色能力 | `viewer` 读；`editor` 读写业务数据与导出；`owner` 另有成员/邀请/空间设置/导入/回收站/清空/审计 |
| 空间读取 | 非成员访问 `GET /workspaces/{id}` 返回 **404**（不泄露存在性）；是成员但无操作权限才返回 403 |
| 空间更新 | `PATCH /workspaces/{id}` 需 `If-Match`（workspace.version）：缺 428，过期 412 + `currentVersion` |
| 成员变更 | Owner 可改角色/移除成员；成员可移除自己（退出空间）；最后一位 Owner 不可降级或移除 → 409 `LAST_OWNER_PROTECTED` |
| 并发保护 | 角色变更与移除在事务内 `SELECT … FOR UPDATE` 锁成员集合，避免并发移除最后 Owner |
| 移除成员 | 同时吊销该用户全部会话（下一请求 401） |
| 邀请 | 只能邀请 `editor` / `viewer`（直接给 Owner 返回 422，所有权转移另立流程）；令牌 32 字节、只存哈希、48 小时、一次性；列表**不回显令牌** |
| 接受邀请 | `POST /auth/invitations/accept` 公开 + 豁免 CSRF（持有型令牌）：已有账号只建成员关系；新账号必须同时设置符合策略的密码 |
| 邀请重发 | 同空间同邮箱再次邀请会作废旧令牌（只保留最新一条） |

## 3.4 项目进度与归档（C-17，F12 补充）

| 项 | 决定 |
|---|---|
| 进度计算 | `progressManual=true` → 直接用 `manual_progress`（0 合法）；`false` → 完成数／有效任务数四舍五入，无任务为 0 |
| 模式切换 | 切到手动必须给 0～100；切到自动时清空 `manual_progress`（数据库 CHECK 也会拒绝自动模式下的残值） |
| 归档 | 新增 `projects.archived_at`（迁移 `20261103070000_project_archive`），与软删除 `deleted_at` 区分：归档项目默认不出现在列表，`filter=archived` 可查 |
| 无活动 | 按空间时区的业务日计算：`diffDays(businessDate(lastActivityAt), businessDate(now))`；≥7 天 `inactive=true`，`filter=inactive` 可筛 |
| 活动时间 | 项目自身更新、关联任务／知识／台账内容变化时更新 `last_activity_at`（提供 `ProjectService.touchActivity` 给后续模块调用） |
| 校验 | `repo` 只接受 `http(s)://…` 或 `owner/name`，≤300；`color` 只接受 `#RRGGBB`；`nextStep` 单行 ≤200；`stack` ≤10 项、每项 ≤32；失败一律 422 且不落库 |
| 权限 | 读：任意成员；写／归档／软删除：`business.write`（editor+）；跨空间或已删除 → 404 |
| 分页 | `limit` 默认 20 最大 100；游标为 `(last_activity_at, id)` 的 base64url 编码，绑定排序 |

## 3.5 任务状态、日期与幂等（C-18，F14 补充）

| 项 | 决定 |
|---|---|
| 完成/撤销 | `status='done'` 时服务器写入 `done_at`；改回 `todo/doing` 时清空；数据库 CHECK 兜底 |
| 改期 | 支持 `dueDate`（YYYY-MM-DD）与 `shiftDays`（整数，按业务日加减）；跨月/年/闰年由 `@aiwb/domain` 计算；不存在的日期（如 2026-02-30）返回 422 |
| 幂等键 | 创建任务必须带 `Idempotency-Key`（≤128 位 `A-Za-z0-9._:-`）；同键同体返回首次结果并标记 `replayed:true`；同键不同体 → 409 `IDEMPOTENCY_KEY_REUSED`；记录保留 7 天 |
| 幂等实现 | `runIdempotent()` 在事务内占位 → 执行 → 写回响应；并发同键靠唯一约束冲突后回读 |
| 昨日顺延 | `POST …/tasks/postpone-yesterday`，`dryRun=true` 只统计；确认时单事务，若受影响行数与预期不符则整体回滚（409） |
| 项目活动 | 任务创建/更新会更新所属项目 `last_activity_at`（复用 F12 的 `touchActivity`） |
| 归档项目 | 归档项目下的任务仍可读取与编辑（归档只影响项目列表） |

## 3.6 今日聚合与阈值（C-19，F15 补充）

| 项 | 决定 |
|---|---|
| 业务日 | 一律由服务端按 `workspaces.timezone` 计算；请求头里的客户端时区被忽略 |
| 逾期 | `due_date < 今日` 且 `status != done` 且未删除（今日到期不算，即“逾期 > 0 天”） |
| 停滞 | `status = 'doing'` 且 `updated_at < now - 3 天`（恰好 3 天不算，即“停滞 > 3 天”） |
| 草稿超期 | `status = 'draft'` 且 `created_at < now - 7 天`（恰好 7 天不算） |
| 计数 | 各桶独立统计；`urgentCount` 按 id 去重（同一任务可能同时逾期与停滞），避免重复计数 |
| 草稿 | 知识条目不属于任务；任务总数（`openTasks`）不含草稿 |
| 列表上限 | 每个紧急桶最多返回 20 条，排序稳定（逾期按截止日升序、停滞按最久未动、草稿按创建时间升序） |

## 3.7 开发日志与分页（C-20，F17 补充）

| 项 | 决定 |
|---|---|
| 作者 | 始终取会话用户；请求体用 strict schema，出现 `authorId` 等未知字段 → 422，无法伪造 |
| 幂等 | 创建需 `Idempotency-Key`；同键重试只保存一条；不同键（不同操作）即便内容相同也各自保留 |
| 校验 | `minutes` 1～1440；`savedMinutes` 0～1440（缺省等于 `minutes`）；`effect` 1～5 的整数；`recordDate` 不得晚于空间业务日；`tool`/`scene` 为小写标识（≤32） |
| 筛选 | `projectId`、`from`/`to`（DATE）、`tool`、`scene`；`from > to` → 422 |
| 游标 | 游标内含筛选指纹；换筛选条件复用旧游标 → **400 MALFORMED_REQUEST**（避免跨筛选翻页错乱） |
| 排序 | `record_date DESC, created_at DESC, id DESC` |
| 汇总 | `GET …/ledger/summary` 返回条数、总投入、总节省、平均效果与按工具分布 |
| 一致性 | 记录变化更新所属项目 `last_activity_at`；软删除后详情 404、列表不含 |

## 3.8 时间戳读取修正（C-21，F17 附带修复）

Prisma 7 的 `@prisma/adapter-pg` 读取 `timestamptz` 时会丢失时区偏移，把数据库会话时区下的本地时刻当作 UTC。会话时区为 `Asia/Shanghai` 时，所有时间戳读回都晚 8 小时（实测 `select now()` 为 08:04Z，适配器读成 16:04Z）。

- 影响：会话过期、`done_at` 的“今日完成”边界、`last_activity_at` 的“几天未活动”、幂等记录过期等所有时刻判断
- 处理：连接固定 `options: '-c timezone=UTC'`（`apps/api/src/common/prisma-adapter.ts` 统一构造），Postgres 以 `+00` 输出，解析即正确
- 业务日的“空间时区”语义仍在应用层用 `@aiwb/domain` 显式计算，不受该设置影响

## 3.9 知识条目状态机与标签（C-22，F19 补充）

| 项 | 决定 |
|---|---|
| 状态 | 仅 `draft / verified / archived`（与 F05 枚举一致，不引入 reviewing） |
| 允许转换 | `draft→verified`、`draft→archived`、`verified→draft`、`verified→archived`、`archived→draft`；其余（含原地转换、`archived→verified`）→ **422 `ENTRY_STATE_INVALID`**，`details` 返回 from/to/allowed |
| 转换入口 | 只走 `POST …/entries/{id}/status`；普通 PATCH 的 strict schema 不接受 `status`，避免编辑顺手绕过校验 |
| 转 verified 条件 | 标题、摘要、正文均非空，否则 422 `VALIDATION_FAILED` 并在 `fieldErrors` 指明缺失字段 |
| 草稿 | 允许空标题／摘要／正文（先记后补）；数据库只保留长度上限，完整性由 `entries_verified_complete_ck` 在 verified 时保证 |
| 正文上限 | **20480 字节**（UTF-8 按字节，不是字符），20481 → **413 `PAYLOAD_TOO_LARGE`** |
| 标签 | 归一化：去首尾空白、去 `#`、折叠内部空白、转小写；每条最多 10 个、每个 ≤32 字；同空间内共享 Tag 行，重复自动去重 |
| 关联 | `projectId` 必须是同空间且未删除的项目，否则 422；跨空间读取条目 → 404 |
| 版本 | `PATCH` 修改正文时，先把**旧正文**写入 `entry_revisions`（含 `sourceVersion`），再更新条目 |
| 条件写 | 更新／改状态／删除需要 `If-Match`：缺 428、过期 412 且返回 `currentVersion` |
| 幂等 | 创建需要 `Idempotency-Key`，同键重试不新增条目 |

## 3.10 正文修订与回滚（C-23，F21 补充）

| 项 | 决定 |
|---|---|
| 修订触发 | 仅当 `body` 发生变化时写入一条修订（保存**修改前**的正文）；只改标题/摘要/标签不产生修订 |
| 保留策略 | 每个条目保留**最近 5 条**修订；写入与裁剪在同一事务内完成，避免“写入了但没裁剪” |
| 回滚接口 | `POST …/entries/{id}/revisions/{revisionId}/restore`，需要 `If-Match` |
| 回滚顺序 | ①校验版本（过期 412）→ ②**先保存当前正文**为新修订 → ③替换为目标修订正文、版本 +1 → ④裁剪到 5 条；全部在一个事务内，失败整体回滚 |
| 回滚可逆 | 因为回滚前保存了当前正文，“恢复旧版”之后仍能再恢复到刚才的内容 |
| 错误 | 修订不属于该条目或不存在 → 404 `REVISION_NOT_FOUND`；跨空间条目 → 404；缺 If-Match → 428；版本过期 → 412 |
| 列表 | `GET …/entries/{id}/revisions` 返回最近 5 条（含正文、字节数、源版本、保存时间），供界面预览 |

## 4. 当前契约维护

当前OpenAPI由实际Controller/Zod输入生成，并已执行OpenAPI3.1标准校验。真实PG/前端类型与页面回归共同核对调用行为。响应data仍为通用信封，不作为完整自动SDK生成来源；原草案与生成边界见[OpenAPI与实现说明](OpenAPI与实现说明.md)。

新增接口需更新路由索引、请求/响应说明及测试；破坏性变更必须明确评估，不以草案字段冒充已实现字段。
