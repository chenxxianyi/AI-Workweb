# ADR-0005 · 业务日与空间时区

- 状态：已接受（F03）
- 日期：2026-11-03
- 关联：R06、R07、R18、R29；数据库与接口设计第 1、3 节

## 背景

「今日」「逾期」「近八周」必须对同一空间的所有成员一致。若用浏览器本地时间，跨时区成员会看到不同业务日期；若把 `2026-11-03` 当成 UTC 时刻，会产生 ±8 小时偏移。

## 决策

1. **业务日期一律用 PostgreSQL `DATE`**（`due_date`、`log_date`、`record_date`），不使用 `TIMESTAMPTZ` 表示“某一天”。
2. **时间戳一律 `TIMESTAMPTZ`，存 UTC**；API 输出带 `Z` 的 ISO 8601；响应中的 `date` 型字段为 `YYYY-MM-DD`。
3. **业务日由空间时区推导**：`workspaces.timezone`（IANA，默认 `Asia/Shanghai`）。后端提供 `businessDate(now, tz)`：
   - 用 `Intl.DateTimeFormat('en-CA', { timeZone: tz, year:'numeric', month:'2-digit', day:'2-digit' })` 得到 `YYYY-MM-DD`（`en-CA` 天然输出 ISO 顺序），不手写时区偏移表。
   - 所有「今日」查询、紧急判定、月度与周聚合都调用同一函数，禁止各处自行拼接日期。
4. **周起点为周一**：近八周序列以业务日所在周一为终点向前推 7 周，缺周补 0（返回 `{weekStart, count, savedMinutes}`）。
5. **时区变更**：仅 Owner 可改，需二次确认并写审计（`workspace.timezone_changed`，记录前后值与业务日）；变更不重算历史记录的 `DATE` 字段，只影响未来的「今日」判定。
6. **`Intl` 不引入日期库**：`packages/domain` 提供纯函数（`businessDate`、`addDays`、`startOfWeek`、`weekRange`、`monthRange`），用 `Intl` + `Date.UTC` 实现，全部有单元测试（F38 补齐边界：闰年、月末、UTC 跨日、DST 无关性）。

## 后果

- 纯函数必须只依赖 `Intl` 与整数运算，禁止 `new Date('YYYY-MM-DD')`（会被解析为 UTC 午夜）。
- 数据库查询用 `due_date < $today::date` 形式，比较在 SQL 内完成，避免 Node 侧时区换算。
- 测试需固定 `TZ` 环境变量不受宿主影响：单元测试显式传入 `now` 与 `tz`，不读系统时区。

## 替代方案

| 方案 | 未采用原因 |
|---|---|
| dayjs + timezone 插件 | 增加依赖；本项目只需 5 个纯函数 |
| 存 UTC 时间戳表示业务日 | 跨日边界产生 ±8 小时错误，正是本 ADR 要避免的问题 |
| 用浏览器本地时区 | 多成员不一致，违反 R06 |
