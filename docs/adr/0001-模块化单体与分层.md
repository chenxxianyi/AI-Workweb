# ADR-0001 · 模块化单体与分层边界

- 状态：已接受（F03）
- 日期：2026-11-03
- 决策者：开发执行人；业务验收人复核
- 关联：R02、R26、R27；方案第 4、6 节

## 背景

本期是 1～10 人私有部署，单台服务器、一个工作空间为主。需要真实事务、空间隔离和可审计的变更，但不需要微服务、Redis 或消息队列的运维成本。团队只有一名开发者（加 AI 编码代理），拆分过度会让回归成本超过收益。

## 决策

1. **一个后端进程、一个代码库、一个镜像**，通过不同启动命令区分 `api` 与 `worker`（导入导出、清理任务）。两者共享 Prisma schema 与 Service 层。
2. 分层强制：`Controller`（协议、DTO、状态码）→ `Service`（授权后的业务与事务）→ `Repository`（每个查询必须显式带 `workspaceId`）。
   - Controller 不写业务规则、不直接调 Prisma。
   - Repository 方法签名必须包含 `workspaceId`，禁止「先按 id 查、再判断空间」。
   - Service 不做 HTTP 语义（不拼响应封装、不读 header）。
3. 前端不直连数据库；所有数据经 `/api/v1` 同源访问。前端只做展示、表单状态与离线队列，不做权限裁决。
4. 后台任务走数据库任务表 + 租约（lease）+ 行锁领取，禁止依赖进程内计时器完成关键工作。
5. 本期不启用数据库 RLS；以 Repository 边界、复合外键（`workspace_id` 参与）与越权集成测试为防线。启用 RLS 需单独立项（连接池事务上下文、非 owner 运行账号）。

## 后果

- 单进程故障影响全部功能：接受，靠健康检查、重启与备份恢复（R28）覆盖。
- 事务边界集中在 Service，测试需覆盖真实 PostgreSQL（禁止用内存数组替代）。
- worker 与 api 同镜像，多实例部署时靠租约避免重复执行。

## 替代方案与未采用原因

| 方案 | 未采用原因 |
|---|---|
| 微服务拆分 | 单机部署、10 人规模；运维与分布式事务成本不成比例 |
| 服务端渲染（Next.js） | 内部工具无需 SEO；SPA 更简单，静态资源可被 Service Worker 缓存 |
| 启用 RLS 作为主防线 | 需要额外连接池上下文设计；本期用 Repository + 复合外键 + 集成测试 |
