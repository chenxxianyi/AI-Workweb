# ADR-0004 · 条件写（If-Match）、幂等键与事务边界

- 状态：已接受（F03）
- 日期：2026-11-03
- 关联：R05、R12、R15、R20、R23、R26；数据库与接口设计第 4、6 节

## 背景

多设备并发编辑时必须避免静默覆盖；断网重试不能重复新建；跨表操作（沉淀、回滚、导入、成员变更）必须原子。客户端时间不可作为冲突裁决依据。

## 决策

1. **版本与 ETag**
   - 可编辑实体带整数 `version`，创建为 1，每次业务内容变化 +1（统计类字段如 `use_count` 不递增正文版本）。
   - `GET` 详情返回 `ETag: "<version>"`；`PATCH`／`DELETE`／`restore` 必须带 `If-Match`。
   - 更新语句形如 `UPDATE ... WHERE id=$1 AND workspace_id=$2 AND version=$3 AND deleted_at IS NULL`；影响行数为 0 时区分：不存在／无权限 → 404，版本不符 → 412（返回当前 `version` 与可授权字段）。
   - 缺少 `If-Match` → 428 `PRECONDITION_REQUIRED`。
2. **幂等**
   - 作用域：`user_id + workspace_id + scope + key`；`request_hash` 覆盖业务体（排除 CSRF 头等易变头）。
   - 首次请求以唯一约束占位；业务变更与结果引用同事务提交。相同 key 不同体 → 409 `IDEMPOTENCY_KEY_REUSED`。
   - 记录默认保留 7 天；离线事件同样 7 天，超期不自动重发（转人工确认／导出），避免过期去重导致重复执行。
   - 结果未知时客户端用**同一 key** 重试或查询状态；不得换新 key。
3. **事务边界**（全部在 Service 内，使用单个交互式事务）
   - 沉淀：校验任务与权限 → 建条目 → 建 `task_entries` → 任务 `version+1` → 审计 → 幂等结果。
   - 回滚：版本校验 → 当前正文入修订 → 选中正文成为当前 → 裁剪至 5 条 → `version+1` → 审计。
   - 成员：`SELECT ... FOR UPDATE` 锁空间成员集合 → 校验至少一个 owner → 变更 → 吊销受影响会话 → 审计。
   - 导入：锁空间导入范围 → 重验 `plan_hash` 与触及实体版本 → 按外键顺序合并 → 关系／统计 → 映射 → 审计 → job 成功；任一步失败全部回滚。
   - 清空：Owner 重新认证 → 确认空间名 → 事务清空该空间业务与关联 → 保留身份与成员 → 审计。
4. **失败语义**
   - 事务失败返回稳定错误码，不吞错；业务失败后另写 job 失败状态（不在回滚范围内伪装成功）。
   - 进程中断的作业靠租约过期重领，同一 job 的业务提交至多一次（以唯一约束 + 幂等记录保证）。

## 后果

- 客户端必须保存并回传 `version`；前端把 `version` 放进实体缓存，不做本地自增猜测。
- 412 需要 UI 支持对比与合并（已由 F02 原型定义三出口）。
- 所有写接口都要有幂等或条件写二选一（创建类用幂等键，更新类用 If-Match），OpenAPI 中逐一标注。
- **范围澄清（F03 契约冻结 C-05）**：`If-Match` 只适用于带 `version` 的可编辑实体（workspace、project、task、entry、ledger、preference、member）。`User`、`Session`、`Invitation`、`Tag`、`EntryRevision`、`EntryUsage`、`AuditEvent` 不带 `version`：不可编辑者（审计、修订、统计）只追加不修改；可撤销者（会话吊销、邀请撤销）以自然键 + 幂等键控制，幂等键相同即不重复执行。

## 替代方案

| 方案 | 未采用原因 |
|---|---|
| `updatedAt` 乐观锁 | 同毫秒并发无法区分；受客户端时钟影响 |
| 悲观行锁（长事务） | 编辑过程中占用连接与锁，跨设备体验差 |
| 最后写入获胜 | 违反 R23“不静默覆盖” |
